# Project: In-memory bitemporal account ledger core

## Goal
An append-only, bitemporal account ledger built as an assessment exercise. The
engine is a pure function of the event stream: replaying the ten-event, six-day
stream is deterministic, and every figure in the documents is reproducible from
a `go run`.

There is no web layer, no persistence, no UI and no database. The brief forbids
them, and everything the boilerplate supplied to serve those layers has been
deleted rather than left as scaffolding.

Read [README.md](README.md) first for what the engine produces and why. This
file is the working agreement for changing it.

## Rules
- Do not add new libraries without consulting me
- Do not create new util or helper functionality without consulting me
- Do not add a layer the brief forbids — no HTTP, no database, no config files,
  no logger. If something seems to need one, raise it instead of building it
- Wait for my command before restructuring a module; do not refactor modules I
  have not asked about
- Run the tests only when I ask
- Every number the engine uses lives in `config/`, 1:1 with NUMBERS.md. Never
  inline a constant at its use site

## Stack
- Go 1.25+, standard library only for the engine
- `shopspring/decimal` — exact money arithmetic, wrapped by `entity.Money`
- `stretchr/testify` (`assert`, `mock`), `mockery` (testify template),
  `brianvoe/gofakeit` — tests only
- Nothing else. No gin, no MongoDB, no viper, no Elasticsearch, no plugin system

## Architecture

### Layers
Dependencies point inward only: `main` → service → repository interface ←
repository implementation.

- **`app/entity/`** — pure value types and filters. `Money`, `Event`,
  `LedgerEntry`, `Accrual`, `Authorization`, `SplitInstalments`, and the
  `XFilter` structs. No framework dependencies, no I/O
- **Repository** (`app/module/*/repository.go`) — interface plus an unexported
  in-memory struct. Storage only: no business rules, no error taxonomy
- **Service** (`app/module/*/service.go`) — all behaviour. Owns the coded
  errors and translates repository sentinels into them
- **`app/presenter/`** — text rendering of the report
- **`main.go`** — composition root and nothing else. No business logic

There are no controllers and no routes: those are the REST delivery layer, and
there is no transport. There is no `app/model`: that layer is the database
representation, and with no database the entity is the stored form.

### Module graph
The graph is a DAG and must stay one:

```
account   ledger
             ^
             |
   +---------+---------+
   |         |         |
authorization  fee  interest
   |         |         |
   +---------+---------+
             ^
             |
           replay
```

`account` and `ledger` depend on nothing. `authorization`, `fee` and `interest`
each depend on `ledger`. `replay` depends on all of them; nothing depends on
`replay`. This is what keeps append-only honest — the journal cannot be made to
care why an entry exists.

### Append-only is enforced by interface shape, not convention
`ledger` and `rejection` expose `Create` and `Read` and deliberately nothing
else. There is no `Update`, no `Delete`, and no method that takes a sequence
number and writes to it: a correction is a new entry with the opposite sign.
The operation that would rewrite history does not exist to be called. Do not
add one.

`authorization` is the module with a genuine `Update` — a live record moving
APPROVED → SETTLED is a state change, not a rewrite of history.

## Conventions

### Module layout
One folder per module under `app/module/`, each holding exactly two files:

```
app/module/<name>/
  service.go       behaviour, the Service interface, the module's coded errors
  repository.go    the Repository interface and its in-memory implementation
  mock/            generated by mockery, committed
  test/            package <name>_test, where the module has tests
```

No topic files and no helpers alongside. If it is behaviour it goes in the
service; if it is storage it goes in the repository; there is nowhere else.

### Interfaces
Both `Service` and `Repository` follow the same shape: exported interface,
unexported struct, `NewService` / `NewRepository` returning the interface.

CRUD naming is `Create` / `Read` / `Update` / `Delete`, and a module implements
only the operations it legitimately has:

- `Create(ctx, entity.X) (entity.X, error)`
- `Read(ctx, entity.XFilter) ([]entity.X, error)` — **all filtering goes
  through the filter struct**. No `ReadBy...`, no `List`, no `All`, no `Get`
  taking a bare ID. A zero-valued filter field means "no constraint"
- `Update(ctx, entity.X) (entity.X, error)`
- `Delete(ctx, id string) error`

A service that also has domain behaviour puts the CRUD block first, then the
domain methods below it with a doc comment each (`fee.Assess`,
`authorization.Authorize`, `ledger.Post`, `interest.Accrue`).

Filters live together in `app/entity/filter.go`, one `XFilter` per read. There
is no pagination — pagination is a transport concern and this core has no
transport.

### Errors
- Coded errors only, via `apperror.New(code, message, cause...)`. Codes are
  registered in `apperror/code.go`: 1xxx request, 2xxx domain validation, 3xxx
  internal
- The repository returns package-level sentinels (`ErrNotFound`,
  `ErrAlreadyExists`) declared in the *service* file; the repository stays free
  of the taxonomy so another store could reuse it unchanged
- Services wrap: `apperror.New(apperror.ErrUnexpected, "read account error", err)`
- A refused instruction is **not** a failure. It is recorded through the
  `rejection` module and reported under its day. Only a module that genuinely
  cannot proceed returns upward to `main`
- Return explicit errors. No panics except at startup

### Money
`entity.Money` wraps `shopspring/decimal` and adds one invariant: every amount
is quantised to its own currency's scale at construction, so sub-minor-unit
dust cannot enter the ledger. AED is 2 places, BHD is 3, taken from ISO 4217
exponents and never inferred from a value. Never do ledger arithmetic on
`float64` or on a raw `decimal.Decimal`.

### Tests
- External test package (`package ledger_test`) in a `test/` subfolder
- Plain `testing` with `t.Run("when ... then ...", func(t *testing.T){...})`
  subtests and `testify/assert`. Not `testify/suite`
- **Behavioural tests** (`app/module/replay/test/`) wire the real in-memory
  repositories the same way `main` does — the arithmetic is the point there,
  and a wiring mistake in `main` is then a wiring mistake in the tests too
- **Module tests** (e.g. `app/module/ledger/test/`) mock the repository with
  the generated `mock.NewMockRepository(t)` and `EXPECT()`, to drive the error
  paths a working store never takes
- `gofakeit` for fixtures where the value is arbitrary (`gofakeit.ErrorDatabase()`)
- Mocks are committed, unlike in the originating boilerplate, so `go test ./...`
  works on a fresh clone with only a Go toolchain. `make generate-mock`
  regenerates them
- `TestKnownGap_OverdraftFeesSurviveReversalOfTheirCause` **is expected to
  fail**. It is the deliberately failing test the brief asks for, an argument
  against the specification. Do not "fix" it

### Comments
Comments here explain *why a decision was taken*, especially where the obvious
alternative was rejected — not what the line does. Match that density and
register when adding code. The package comment on `service.go` states what the
module owns and why it is a module of its own.

## Commands
```bash
go run main.go                                              # replay, default policy
LEDGER_FEE_REVERSAL_POLICY=on_cause_reversal go run main.go # criterion-6 policy
go test ./... -count=1                                      # one failure expected
go test ./... -count=1 -skip 'TestKnownGap_'                # must be green
```

`make run`, `make run-reversal`, `make test`, `make verify` and
`make generate-mock` wrap these. The `go` commands are the primary path: the
`make test` targets regenerate mocks first and so need mockery installed.
